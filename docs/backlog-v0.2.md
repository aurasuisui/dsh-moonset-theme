## B1 毛玻璃材质（**2026-11-23 改判：由本插件承担，不再做独立包**）

> ⚠ 本节写于「玻璃=独立插件」时期。2026-11-23 用户决定：玻璃并入本插件，作为皮肤层分阶段交付；
> 下面的方案（材质面、::before、菜单座位）仍然有效，只是**落点变了**。新排期见 `docs/plans/` 下的新契约（待定稿）。

**问题**：用户真正想要的是**毛玻璃材质**（面板半透、背景模糊、描边高光），而不是换一套颜色。
0.1.0 只交配色，深色底 + 纯色面板在观感上"离材质还差一层"。

**为什么现在不做**：材质在 catppuccin 里是独立子系统——`glass.module.css` 131 KB，
外加一身 `[data-dsh-glass]` 钩子和自己的开关/持久化。把它移植进来会把"配色插件"变成
"皮肤插件"，且与新配色没有任何语义关系（已决 #6）；用户也明确说"无法兼容就不兼容"，
即不要求与 catppuccin 的材质层共存（已决 #3）。0.1.0 的收尾口径是「能选 / 能记住 /
重启恢复 / 首帧不闪」（已决 #16）。

**建议做法**：单独立项、独立包（例如 `dsh-moonset-glass`），只做材质层：
自己的 `[data-moonset-glass]` 钩子、`backdrop-filter`、面板 α/描边高光、一个开关 +
持久化。主题插件继续只写 `--dsw-*`，两者通过 token 名对齐、不互相 import。
验收先在小样页做像素对照，再进真机。

## B2 环境光晕（月晕与琥珀辉光）

**问题**：用户看到设计稿/期望里的"月晕 / 琥珀辉光"——画布角落的柔和光斑、渐变尾。
主题插件做不出来，观感上会"少一口气"。

**为什么现在不做**：主题插件只能改 token（颜色值），做不了 `position:fixed` 的渐变层、
`filter: blur()` 或多层叠加；`moon` 锚点目前只被钉在 `--dsw-static-amber-500` 上，
没有任何可见的"光"（已决 #16）。硬塞进 token 只会得到一块死色。

**建议做法**：与 B1 同一个皮肤层插件里做（或另起 `dsh-moonset-glow`）：几个
`position:fixed` 的伪元素/覆盖层 + 低透明度径向渐变 + 可选 `backdrop-filter`，
颜色取自 `--dsw-static-amber-500` 与 `accentGlow`，默认关闭、可调强度。
需要一份真实的合成器/滚动性能测量，避免长列表滚动掉帧。

## B3 正文颜色可调

**问题**：用户实测"正文颜色不变"——想要的是把正文（`inkPrimary` 一族）也做成可调，
而不是只有浅/深两套固定映射。

**为什么现在不做**：0.1.0 的设置区固定三个按钮（浅色 / 深色 / 跟随系统），
`Config` 只有一个 `choice` 字段；要支持正文色可调，需要第二个字段 + 一层
`overrideTokens`（或生成期参数）+ 新的设置 UI + 一整套对比度回归（22 条契约要能
在任意正文色下仍成立）（已决 #16）。

**建议做法**：加 `Config.ink`（枚举或受限色值），客户端把它合成进
`--dsw-alias-label-*` / `--dsw-static-neutral-*` 相关的覆盖层，优先级明确写在
[架构 §5](architecture.md) 的层叠规则里；先把对比度契约参数化（正文色作为输入），
再加 UI。要处理与 follow 层同时存在时的层序。

## B4 1500ms 再断言窗口的盲区

**问题**：用户在"本地写入后 1500ms 内"真去官方 Appearance 点 light/dark/system 时，
这次点击会被当成设置回声再断言掉，**不会**镜像成 `off`；自愈要等下一次任意设置写入，
纯静置不自愈（`RESTORE_WINDOW_MS = 1500`，`src/client/durable.ts`）。

**为什么现在不做**：0.1.0 的退出条件是"三态各选一次、选完 10 秒内不回弹"；这个窗口
正是修回弹必须付出的代价，收紧它需要新的判据（见下），而 0.1.0 已经冻结范围。

**建议做法**：三选一——(a) 再断言成功后立即关窗（`lastWriteAt = 0` 或"本波次已处理"标记）；
(b) 让官方点击带 revision 证据（若设置服务能给出"这次 change 来自外部"的信号就采信）；
(c) 把窗口从"时间"改成"事件"（等到 `form` 回声落定即关窗）。任一方案都要先在
`tests/echo.spec.ts` 写一条会失败的用例。

## B5 再断言上限是每波次

**问题**：`REASSERT_LIMIT = 3` 是**每波次**计数（用户 pick 清零），窗口内连续第 4 次被
冲回就停手并 warn 一次，官方主题留在界面上（实测不触发）。

**为什么现在不做**：上限本身是防止"再断言 ↔ adopt"互相喂食的安全阀；换更聪明的策略
需要先有 B4 的判据，否则只是把死循环风险换个地方。

**建议做法**：改成指数退避 + 把"最后一次再断言失败"记进持久状态，下一次启动时
显式提示（而不是只在 console 里 warn）；或者与 B4 一起解决。

## B6 多窗口不同步

**问题**：挂载后另一个窗口改 section，本窗口按钮不刷新，也没有冲突提示
（M5 债 3 / M5.1 债 4；用例只证了 `read()` 会采纳新值）。

**为什么现在不做**：0.1.0 的单窗口体验已经完整；跨窗口需要决定"谁是权威"（后写赢？
弹提示？）以及一个广播通道，属于新交互，不在收尾范围。

**建议做法**：设置表单本身能订阅变化（`durable.subscribe` 已在用它），把 section 的
渲染改成订阅式（当前 `injected()` 只在渲染时读一次），再补一条"另一窗口改了 →
本窗口重渲染"的用例；冲突策略建议"后写赢 + 一次性提示"。

## B7 无设置表单时的点击与晚绑定

**问题**：宿主没有 `configForms` 表单时点击只 warn、不记忆（M5 契约规定）；如果
"先点击、后绑定成功"，绑定时的 `seed()` 会把文档里的旧值采纳回来，看起来像"点了没用"。

**为什么现在不做**：契约明确"无 form 只 warn 不记忆"，且这是宿主降级路径；
0.1.0 的真机（桌面壳）有 form。

**建议做法**：绑定成功后若存在用户已表达的意图（`pendingLocal` 之外的"本次会话点击"），
优先把它落盘一次；补一条"先点后绑"的用例。

## B8 镜像路径在 `theme/change` 派发栈内撤层

**问题**：`mirrorOfficialPick()` 里的 `follow.disable()` 在 `theme/change` 派发栈内执行，
真实宿主会同步再 publish 一次；目前靠 `read()` 已返回 `off` 让它变成 no-op（M5.1 债 2）。
计划已决 #5 的"离开派发"理想形态没做到，是有意换取的（加窗口会让变异 #3 失效）。

**为什么现在不做**：这是一次"用正确性换可测性"的已知取舍，改法会动到 M5.2 的再断言
窗口语义，必须与 B4 一起设计。

**建议做法**：把撤层也挪到 `queueMicrotask`，用与再断言相同的 `active` / 合并标志；
同时补一条"派发栈内不再 publish"的用例（并保留现有变异 #3 能变红）。

## B9 `theme/change` 只在设置区装配后才订阅

**问题**：`theme/change` 的订阅在 `wireSettings` 里，需要 `slots` + `locale` 都存在；
缺任一个，镜像与再断言都不工作——"镜像依赖设置区装配"的隐性耦合（M5.1 债 3）。

**为什么现在不做**：真实客户端两者都由 `dsh.client.inject` 保证；这条只在裁剪宿主上出现。

**建议做法**：把订阅拆到独立 effect（只依赖 `ctx.on` 与 theme），设置区装配失败不影响
回声守卫；补一条"无 slots 时仍能再断言"的用例。

## B10 启动期会写一次官方设置

**问题**：`follow` 的开机恢复会 `setTheme('system')`，即"启动即写用户设置"；语义上必要
（否则跟随层的 OS 半边不活），但它确实改写了官方偏好文档（M5 债 2）。

**为什么现在不做**：不写就没有真正的"跟随系统"；0.1.0 接受这个语义。

**建议做法**：只在 `preference !== 'system'` 时写（当前已如此），并在设置区文案里
说清"跟随系统会把官方 Apperance 偏好设为跟随系统"；或改成不写文档、只在内存里用层
（需先验证 runtime 是否允许）。

## B11 `:root{color-scheme}` 没有发

**问题**：官方唯一的 `color-scheme` 设置点是 boot 行的 `:root{color-scheme:light|dark}`
（`design-platform.css` 里 `color-scheme` 命中 0）；我们的首帧样式行没有它，所以
"选 moonset-dark 而官方偏好是 light"时，UA 控件/滚动条会短暂按 light 画（M6 债 1）。

**为什么现在不做**：M7 真机结论是"看得见就补"；真机复验尚未完成，先不盲改首帧契约。

**建议做法**：在固定风味块前缀 `:root{color-scheme:light|dark}`（一行；并列 `:root` 同为
(0,1,0)，我们后渲染，等特异性后写胜），follow 模式按媒体查询各发一枚。改完必须重跑
`tests/boot.spec.ts` 的 228 条与双选择器断言。

## B12 macOS 振动层

**问题**：样式表 237 个唯一名里有 9 个只出现在 `html[data-platform='darwin'] body`
（0,1,2），在 macOS 上压过我们的两个选择器；那 10 个名字里只有 `--dsw-specific-menu`
与我们的表重叠（M2 债 1 / M6 债 2）。本机是 Windows，无法验证。

**为什么现在不做**：需要一台 macOS 才能验收；0.1.0 明确只在 Windows 桌面壳上验。

**建议做法**：为首帧与主题各发一块 `html[data-platform='darwin'] body` 的覆盖（或把
选择器列表扩到含该前缀），在本机 macOS 上比对菜单/滚动条/工具栏观感；表里那 9 个
名字要单独补值（当前刻意不进双方案表）。

## B13 暗色 overlay 的 α 沿用官方值

**问题**：暗色**描边 / 悬停 / 骨架**那一档的 α（`border-inverted`、`border-l1..l4`、
`interactive-bg-*`、`bg-skeleton`，实测 0.06–0.24）沿用官方值，没按月落暗色的观感调大；
遮罩档（`bg-mask-1/2/3/photo`，0.2–0.88）另算。真机若觉得描边/悬停偏弱，要调的是这档 α
（生成器只换色相、不调 α），不是锚点色（M3 债 1）。

**为什么现在不做**：没有真机观感结论前调 α 是盲调。

**建议做法**：真机复验后按"描边可见 / 悬停可辨 / 不脏"三条各调一档，并重跑 22 条契约
（尤其 `border-l1` 的 ≤1.5 上限）。

## B14 浅色 `menu-surface-fill` 的色差

**问题**：浅色 `--dsw-menu-surface-fill` 为 `rgba(255,255,255,.7)`（源板 `elevated`
就是纯白），与官方 `rgba(252,253,254,.7)` 有 2–3 级差（M3 债 2）。

**为什么现在不做**：属源板语义，不是错误；0.1.0 不为此改锚点。

**建议做法**：若认为菜单"太白"，给源板加一个 `elevatedAlpha` 角色或在生成器里给
菜单材质单独一条规则，而不是改 `elevated`（它同时是卡片色）。

## B15 首帧块体积

**问题**：固定风味块 ≈12 KB、follow ≈24 KB，**每次 index 渲染都内联**，未裁剪；
gzip 后 `lib/index.js` 8.85 kB，当前可接受（M6 债 3）。

**为什么现在不做**：还没到需要优化的量级，且内联是首帧生效的前提。

**建议做法**：若要压，可把 228 条压成"只发与官方不同的键"（需要一份官方基线的
逐键 diff）或改成 `kind:'style'` 的外部资源 + 缓存头；先量一次真实 TTFB 再决定。

## B16 `dsh.client.inject` 缺两条

**问题**：`package.json` 的 `dsh.client.inject` 目前 4 条，缺
`dsh-client-connection` / `dsh-api-remotes`；M5 已真吃 `configForms`，某些宿主组合下
可能出现 `entry(s) did not activate`（M1 债 1 / M5 债 4）。M5、M7 的假宿主都没触发。

**为什么现在不做**：缺哪条取决于宿主版本对表单服务的依赖；0.1.0 的真机启动日志
尚未复验，先不改清单免得引入未验证的依赖。

**建议做法**：按目标宿主的实际依赖补两条，重跑 M7 与真机启动日志（关注
`entry(s) did not activate`）；同时把 `slots.inject` 本身也包进
`tolerantRegistration`（参考实现同形，但重复 section id 现在靠内层 callback 兜）。

## B17 没有 `.gitattributes`，行尾会漂

**问题**：本机 `core.autocrlf=true`，`palettes.ts` 与 `themes/` 会出现"内容相同、行尾不同"
的幻影 M；测试已做行尾归一化（CRLF 检出下 37 条全绿）（M1 债 4 / M3 债 4）。

**为什么现在不做**：0.1.0 用测试归一化顶住了；加 `.gitattributes` 会一次性重写所有
文件的 blob，属于"看起来很安全但会淹掉 diff"的改动，应当单独一次提交。

**建议做法**：`* text=auto eol=lf` + 单独一个"只改行尾"的 commit，跑全量门禁后合并。

## B18 没有 `prepare` 脚本

**问题**：`link:` 安装前必须先 `pnpm build`，否则装进去的包没有 `lib/`
（`lib/` 在 .gitignore 里）；这条已经写进 README 的安装步骤（M1 债 3）。

**为什么现在不做**：`prepare` 在 `link:` 场景下的触发时机依赖包管理器版本，没验证过
不敢写进契约。

**建议做法**：先在一个临时 profile 里验证 `pnpm install` 是否会对 `link:` 依赖跑
`prepare`；确认后再加 `"prepare": "tsdown"`，否则保持"手动 build"的文档口径。

## B19 `extract` 非幂等

**问题**：`scripts/extract-dsw-tokens.mjs` 每次重写 `meta.extractedAt`，跑一次审计就把
`themes/dsw-tokens.json` 弄脏；当前约定是跑完 `git checkout -- themes/dsw-tokens.json`
（M2 债 1）。

**为什么现在不做**：改输出格式会动到 M2 的审计锚点契约（`meta` 被测试断言）。

**建议做法**：把 `extractedAt` 改成可选（`--stamp` 才写），或只在值变化时更新时间；
测试里把该字段排除在比较之外。改前先确认没有下游依赖它。

## B20 `verify` 首行的 `live` 是并集

**问题**：`node scripts/verify-tokens.mjs` 首行 `live` 是 light ∪ dark 的并集，
浅深分叉在首行看不出来（M2 债 2）。测试已用"键集合完全相同"补上这个盲点。

**为什么现在不做**：脚本输出是给审计看的，测试已经兜底；改输出格式要同步改文档里的
"期望输出"。

**建议做法**：`live` 拆成 `live_light / live_dark` 两列，并加一条"两集合相等"的硬断言。

## B21 两份 fiber 共享一次注册

**问题**：同一个 runtime 上重复安装（两份 fiber）共享一份注册与一次释放，不是引用计数：
**先释放的那次生效、后一次 no-op**，主题会消失到下次激活（M4 债 4 / M7 观测原文）。

**为什么现在不做**：真实用户只装一份；这是"重复安装"的边缘形态。

**建议做法**：注册表按 runtime 记 fiber 计数，计数归零才真正 `dispose`；先写一条
"两份 fiber 交错卸载"的用例，再改 `themes.ts` 的 WeakMap 记忆。

## B22 `Config` 的真机投影未验

**问题**：`Config.choice` 的 volatile 投影只证了 schema 形状（单测），真机是否真的投影出
表单、`slots.inject` 是否稳、`order: 40` 的排位是否合适都没验（M5 债 4 / M5.2 债 2）。

**为什么现在不做**：需要重启桌面壳并目视设置区；M7.1 的真机复验尚未完成。

**建议做法**：重启后检查三件事：设置里出现「Moonset 主题」且三个按钮可点、
`order: 40` 的排位符合预期、`ctx.configForms.get('dsh-moonset')` 能读到 `choice`；
把结论写回看板。

## B23 组件没有 React 测试栈

**问题**：仓库没有 `jsdom` + `@testing-library/react`，设置区组件只测到控制器/持久化/
注册元数据，视觉验收靠真机截图（M5 债）。

**为什么现在不做**：0.1.0 的依赖清单刻意保持零 React；加测试栈是新的依赖决策。

**建议做法**：若要回归组件，先引 `jsdom` + `@testing-library/react` 作为 devDependency，
再给三按钮的 `aria-pressed` / 点击回调补用例；否则维持"控制器有测试、组件看真机"的口径。

## B24 版本号有两种含义

**问题**：`meta.dshVersion = 0.2.2-rc.5` 是**桌面壳 runtime** 的版本，不是 npm 全局 CLI 的
`0.2.2-rc.1`；两者混用会得出错误的兼容结论（M2 债 3）。

**为什么现在不做**：字段名已经写进 M2 的审计契约，改名要同步改测试与文档。

**建议做法**：`meta` 增加 `source: 'desktop-runtime' | 'npm-cli'`（或用 `runtimeVersion`
改名），文档统一按来源括注。

## B25 注册表不存 label

**问题**：官方注册表不存主题 label，Appearance 对第三方 id 显示裸 id；我们自己的设置区
用 `MOONSET_THEMES.label` 自渲染，但官方那一行仍是裸 id（M4 债 2）。

**为什么现在不做**：这是宿主注册表的能力边界，插件改不了。

**建议做法**：向宿主提 feature request（`ThemeDefinition.label`）；在那之前文档提醒用户
"官方 Appearance 里显示的是 `moonset-light` 这样的 id"。

## B26 同一时刻只让一方掌权

**问题**：与 catppuccin 同装时，它会回弹第三方主题 id（见
[compatibility.md §2](compatibility.md)），两方同时掌权会互相拉锯。

**为什么现在不做**：这是 catppuccin 的既有行为，不是本插件能改的；用户也接受
"无法兼容就不兼容"（已决 #3）。

**建议做法**：文档写清「切到另一方的主题前，先把这一方关掉」；真机验收沿用
M7.1 的跑法（catppuccin `disabled: true`）。若将来要做"互相让位"，需要两方都改，
属于跨插件协议，不建议单方面实现。

## B27 不做的三件事

- **不把玻璃/材质层移植进本插件**：见 B1，它是独立插件。
- **不做 TUI 主题**（`~/.dsh-tui/themes/`）：`dsh-tui` 只读目录、没有注册 API，
  属于另一条发布面（已知债）。
- **不做 npm 发布 / 打 tag / 合并分支**：任何 `npm publish`、`git push --tags` 都须人类口令
  （非目标）。
